# Developing Stretch

## Build, run and test

Needs JDK 25 for Gradle (`JAVA_HOME`); Gradle provisions the toolchain. Apps run on the JetBrains Runtime 25 (the gallery's run task picks it), whose custom title bar API lets `StretchWindow` draw its own title bar inside a native frame on Windows and macOS. On other runtimes and on Linux the window keeps the system title bar.

```
./gradlew check          # unit, contrast and component tests, generated-code checks
./gradlew :gallery:run   # every component in every theme
./gradlew :gallery:run -Pdevtools=47811   # also serves screenshots of its windows: curl 127.0.0.1:47811/capture
./gradlew :gallery:run -Pgpu              # adds a WebGPU viewport page and opens on it (needs a GPU; Windows)
./gradlew :gallery:run -Pdocuments        # opens on the diff viewer, markdown editor and HTML view
./gradlew :gallery:run -Pdocuments -PjavaHome=<a JDK without JCEF>   # offers to fetch the engine, then runs on it
./gradlew :stretch-web:desktopTest :stretch-mermaid:desktopTest :gallery:desktopTest -Pcef   # also tests the real browser engine, opening a window briefly; pictures land in each module's build folder
./gradlew compileKotlinWasmJs             # compiles for the browser, which check does not
./gradlew :gallery:wasmJsBrowserProductionRun   # the gallery in a browser
./gradlew :gallery:wasmJsBrowserDistribution    # the gallery as a static site, in gallery/build/dist/wasmJs/productionExecutable
```

Without `-Pcef`, tests in `stretch-web`, `stretch-mermaid` and `gallery` run with JCEF hidden (`stretch.modulesWithoutEngine` in `gradle.properties`), so `check` covers an app on a runtime with no engine.

Common tests run on the desktop target only, so `check` needs no browser or Node. Compiling for the browser catches JVM-only calls in common code, which the desktop compile lets through; CI does it in its `web` job. After changing npm dependencies, run `./gradlew kotlinWasmUpgradeYarnLock` and commit `kotlin-js-store`.

IntelliJ IDEA: open the folder; the Gallery and Check run configurations are included.

## Generated code

`stretch-theme/.../Tokens.kt` comes from `design/tokens.json` and `StretchIcons.kt` from `design/icons/*.svg`. Change the source, then run `./gradlew :stretch-theme:generateTokens :stretch-theme:generateIcons`; `check` fails when they are out of date.

`stretch-gpu-native/src/main/java` comes from wgpu-native's headers through jextract, for the symbols in `stretch-gpu-native/bindings.includes`. The build downloads the wgpu-native release named in `gradle/libs.versions.toml` (checked against the SHA-256 in `stretch-gpu-native/build.gradle.kts`) and packs its library into the jar. After changing the version or the symbol list, install jextract 25 and run `./gradlew :stretch-gpu-native:generateBindings -Pjextract.home=<jextract folder>`.

## macOS

No one develops on a Mac at the moment, so the `macos` CI job is how macOS gets seen: it runs `check`, the engine tests and packaging, and uploads pictures of the diff viewer, editor and HTML view as the `macos-engine-pictures` artifact. What only a person can check there: how scrolling in an `HtmlView` feels, since the page scrolls by AWT's wheel events (fine steps included, at the rate Compose uses on macOS) rather than native gestures, and a packaged app, where `restoreEngineFiles` in the Gradle plugin places the runtime's `Frameworks` by its best reading of the layout, unsigned.

## Publishing

Pushing a tag like `v0.1.0` runs `.github/workflows/publish.yml`: it runs `check`, publishes version `0.1.0` to GitHub Packages and creates a GitHub Release. `publishedModules` in the root `build.gradle.kts` lists what goes out, along with `stretch-gradle-plugin`; the gallery and `stretch-devtools` stay out.

To update Mermaid, replace `mermaid.min.js` with `dist/mermaid.min.js` from its npm package and change the version in `NOTICE`.

`stretch-gpu-native` packs the wgpu-native library of the machine that builds it, so the workflow runs on Windows and the published `stretch-gpu` only works there.
