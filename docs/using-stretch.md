# Using Stretch from an app

## Platform

- **Appearance and size.** `StretchTheme(StretchThemes.system(light, dark), scale = size)` follows the OS's light or dark appearance and draws everything at the interface size a person picked. Popped-out drawer windows keep the same size.
- **Drawers that come and go.** Pass `StretchApp` a `placeNewDrawer` and its `drawers` list can change while the app runs: the layout follows through `onLayoutChange`, a new drawer goes where `placeNewDrawer` puts it, and one that leaves is remembered in `FrameLayout.removed`, so it comes back on the same side, at the same width, open or in its window as it was. `addDrawer`, `removeDrawer` and `syncDrawers` do the same on a `FrameLayout` directly, and `ModeLayouts.addDrawer` and `removeDrawer` change every mode and its default at once.
- **Top bar.** `TopBar` and `WindowTopBar` take a `leading` control after the menus and before the document name, such as a picker for what the window shows, and a `center` item centred on the whole bar, such as a search field. As the bar narrows the document name gives way first; then the centre item moves aside to stay clear of both sides, narrows down to 160dp (or its own width, if less) and hides; then actions fold into More. On the desktop title bar both are controls that take clicks. `TopBarActions(commandsKeys = keymap.capsFor(action))` shows the app's own binding for the command palette in its tooltip and menu item; it shows Ctrl K (Cmd K on macOS) unless told, and none for null. `TopBarActions(leading = ...)` puts the app's own actions before the standard ones, such as a notifications bell, and a `BarAction`'s `badge` puts a count or a dot on its button.
- **Search palettes.** `CommandPalette` searches the registry's actions. For an app's own "go to anything", `SearchPalette(query, onQueryChange, onDismiss, placeholder)` gives the same panel with the app's results: `trailing` controls after the field (a count, a `Segmented(compact = true)` scope), `PaletteSection` eyebrows, `PaletteRow`s, `MatchedText` marking what `matchRanges(query, label)` found, and `PaletteHints` key hints in a footer. `scrim = true` dims the window behind it; `onKey` gets every key first, for moving through results. `searchLabels` and `matchScore` rank labels the way the palette does. For a field that suggests as the person types, `fuzzyMatch(query, label)` forgives more: the query's words in any order, a slipped letter in a longer word, and letters in order ranked by how close together they are; it gives a score and the ranges to mark, and `fuzzySearch` ranks items by the best of several labels each. For a search field that lives on a page rather than over the window, `SuggestionPanel(open, onDismiss, width)` drops the same sections and rows under the field without taking the keyboard, so the field keeps typing and handles Up, Down and Enter itself.
- **A strip under the top bar.** `StretchApp(topStrip = { ... })` puts a strip across the whole window between the `topBar` and the frame, above the rails, drawers and viewport, such as a row of the sources a window shows; it draws its own background and the line under it.
- **Long lists in drawers.** A drawer's contents scroll under its header, so a `LazyColumn` or `Tree` there would build every row. Give its `DrawerSpec` `scrolls = false` and the contents get the height under the header instead, docked or in their own window, and do their own scrolling: a `Tree` or `LazyColumn` with `Modifier.weight(1f)` fills what the rows above it leave and builds only the rows on screen. `Drawer(scrolls = false)` does the same for a drawer drawn by hand.
- **Desktop notifications.** `DesktopNotifications.show(title, text, onClick)` shows a notification through the OS, outside the app's windows: a toast on Windows, a banner on macOS. The first one puts the app's icon in the system tray, where it stays until `close()`; a click on the notification or the icon runs the latest one's `onClick`. Where there is no tray, `available` is false and nothing shows. Desktop only.
- **Clipboard.** Mark a part of the app that has its own selection with `Modifier.clipboardTarget(router, handler)`; Ctrl C, X and V (Cmd on macOS) and the router's `actions()` go to whichever target has the focus. Text fields keep their own clipboard. In a browser the clipboard holds text only: custom data stays in the page, and pasting asks for the browser's permission.
- **Pointer over controls.** Every Stretch control shows the normal arrow while the pointer is over it, whatever the content around it shows, such as a dialog header's move cursor or the text beam of code a card of buttons sits in. A control's label is never part of a text selection around it, so dragging over a button in selectable content selects nothing; an app's own control labels itself with `ControlLabel`, and menus keep their text out of selections too. An app's own clickable control shows the arrow with `Modifier.controlPointer()`, and `Modifier.handPointer()` shows the pointing hand over something in running content that takes clicks.
- **Menus.** `BarMenus(menus)` in the `TopBar`'s `menus` slot gives File, Edit and so on inside the bar on Windows and Linux. On macOS `WindowTopBar` leaves them out, and `MacMenuBar` fills the system's menu bar instead.
- **Long menus.** A `Menu` never grows past the window: it takes the room beside its anchor (above it when there is more room there), and when its items do not fit they scroll inside it with Stretch's scrollbar. A menu that fits looks and sizes as before. `MenuPanel(maxHeight = ...)` gives other menus the same limit. A `Menu` has no arrow-key navigation of its own, so an app that highlights items itself (`MenuItem(highlighted = ...)`) scrolls the highlighted one into view itself.
- **macOS.** Ctrl in a `KeyChord` is Cmd on macOS, and key caps show the Mac symbols. Inside `StretchWindow`, `MacMenuBar(menus, registry, keymap, mode)` fills the menu bar from the app's actions and hooks up About, Settings and Quit; it shows nothing elsewhere.
- **Crashes.** An exception that escapes in a `StretchWindow` or one of its pane windows, whether from composing, measuring, drawing, input or an effect, builds that window again instead of ending the app, and goes to `StretchWindow(onCrash = { crash -> ... })` as a `WindowCrash` (by default its stack trace is printed). State the app keeps outside the window's content carries over; state remembered inside starts again. A `PaneGrid` tab whose content started showing just before the crash, or every showing tab when crashes come back within seconds, is held: the pane shows an error mark and a reload in place of its content until the reload is pressed, and `WindowCrash.held` names those tabs. When building again keeps crashing with nothing left to hold, the window closes through `onCloseRequest`, and a pane window's tabs go back to the grid. Compose cannot catch a failure inside one part of a window, so the window is the unit that is rebuilt.
- **Viewport.** Give `Viewport` a `ViewportCamera` for wheel, middle-button and two-finger navigation, and `rulers = true` with guides. Put `Modifier.marquee(camera)` and then `Modifier.transformHandles(...)` on the scene layer.
- **Panes and tabs.** `PaneGrid(layout, onChange, item) { id -> ... }` fills the viewport with panes of tabs, split side by side and stacked as a `PaneLayout` says. The app keys its views by string ids: `item(id)` gives a tab its title, icon and modified dot, and an optional `subtitle`, such as the project a file is from, shown quieter after the title; the content lambda draws the showing tab, keeping each tab's saveable state while another shows. A tab is as wide as its title asks; when a strip is crowded the widest tabs shrink first, cutting titles short (subtitles before titles, with a tooltip giving both whole), and only then does the strip scroll. Tabs drag along a strip, into another pane, or onto a pane's edge to split it, with a preview of where they land; borders drag to resize; a middle-click or the close button closes a tab, and a pane left empty collapses. `paneActions = { paneId -> ... }` puts the app's buttons, such as split or close others, at the end of each pane's strip, and `tabMenu = { id, close -> ... }` adds the app's items for that tab after Stretch's own Close and Move to new window, opened by a right-click, a long press or Shift F10 and the Menu key on a focused tab. `PaneLayout` is plain data (strings, numbers, enums and lists) with pure changes such as `open`, `close`, `move`, `splitWith` and `resize`, so the app keeps it as state and saves it however it likes. Anything outside the grid drags in as a tab too: give the grid `dropTarget = rememberPaneDropTarget()` and the element `Modifier.paneDragSource(target) { TabItem(id, title) }`, and it previews and lands like a tab, onto a strip or a pane's middle, onto an edge to split, or away from the grid into a window of its own (where there is no window host, letting go away from the grid does nothing). The grid opens it with `PaneLayout.place(id, drop)`, or the app passes `onDropItem = { id, drop -> ... }` to create its view first and call `place` itself. Tree rows take it through `rowModifier`. `TabStrip` is the strip on its own, with drag to reorder and arrow keys. Inside `StretchWindow`, a tab let go away from the grid, or sent by its menu's Move to new window, opens in a full window of the app under the pointer: in the taskbar, free to go behind the main window or onto another screen, with the app's title bar, theme and size. The same content lambda draws it there. Its tabs drag back into the grid, or the window's header drags it onto a pane to dock all its tabs; closing it puts them back in the grid. Windows are part of the `PaneLayout`, with their bounds, so they reopen where they were (`detach`, `moveWindow`, `dockWindow`, `returnWindow`, `closeWindow`). In the browser tabs stay in the grid.
- **GPU viewport.** Put a `NativeSurface(state, renderer)` in the `Viewport`: a native window that a `SurfaceRenderer` draws `state` into on its own thread, with mouse, pen and touch passing through to the Compose UI under it. Any GPU API can implement `SurfaceRenderer`; `stretch-gpu`'s `WebGpuRenderer` runs a `GpuScene` with WebGPU. Compose cannot draw over the surface, so the scene draws a `ViewportOverlay` for gizmos and handles, and the app calls `NativeSurfaces.enable()` first thing in `main` so popups open in windows of their own over it. An app's own popups should use `StretchPopup` in place of Compose's `Popup`: it shows them at their final size and place, moving one moves its window without redrawing it, and on Windows they move with a dragged window in the same step rather than trailing it. With `Viewport(nativeContent = true)` the rulers sit beside the surface, the corner slots float over it in popups, and the app adds `guidesOverlay`, `marqueeOverlay` and `handlesOverlay` to its scene's overlay (with `Modifier.marquee(state, camera)` and `Modifier.transformHandleInput` for the pointer side). `Modifier.orbitNavigation(camera)` orbits a 3D camera with the middle button and the wheel; on a touch screen two fingers pan, pinch to move in and out, and twist to turn it. To find what is under a point, cast `camera.ray(at, width, height)` and test it with `Ray`'s plane, sphere, triangle and box hits, or give the surface a `SurfacePickQueue` and draw IDs in `GpuScene.renderIds` to pick on the GPU. Several views can share one surface, and so one swap chain: lay one `NativeSurface` over the whole area with a `Viewport(nativeContent = true)` per view on top of it, then give each view a `setViewport` and `setScissorRect` on the render pass and its own camera (`Mat4.orthographic` for a locked view). On the desktop surfaces are Windows only for now.
- **The web.** `stretchPage(title) { ... }` in a `wasmJsMain` entry point runs the app as a page, and `WindowTopBar` becomes the plain bar with the menus inside it. There are no pop-out drawers and no `MacMenuBar`. A `NativeSurface` is a canvas behind the Compose page, seen through a hole the surface clears, so Compose content and plain popups draw over it and `NativeSurfaces.enable()` is not needed; the scene can still draw a `ViewportOverlay`. Everything runs on the page's one thread, so a `SurfaceRenderer` renders at the browser's animation frame and long work blocks the UI. `webGpuAvailable()` says whether the browser offers WebGPU. A pen reaches Compose with its pressure but as `PointerType.Touch`, with no tilt. A browser keeps some shortcuts for itself, such as Ctrl N, T and W in a tab. Serve the site over HTTPS (`localhost` also works) for WebGPU, the clipboard and file access. Compose downloads fallback fonts from Google Fonts for characters the app's fonts lack.

## Controls

- **Disabled buttons.** `Button(enabled = false)` shows the label and icon faint, keeps its resting fill under the pointer and takes no clicks, in every `ButtonKind`; `IconButton`, `ToolButton` and `Segmented`'s `enabled` do the same.
- **Segmented tooltips.** `Segmented(tooltip = { option -> text or null })` gives each option its own `Tooltip`, shown after the usual hover; options that return null have none.
- **Chips that press.** `Chip(onClick = ...)` presses and ends in a chevron, for a chip that opens a menu of choices (anchor a `Menu` to it); it takes the hover and focus ring of other controls. `Chip(dashed = true)` draws the edge dashed for a tentative value, such as a guess not yet confirmed, and sets the `ChipDashed` semantics property so a test can read it. `Chip(description = ...)` names it for assistive tools.

## Trees

`Tree(roots, rememberTreeState())` shows nested `TreeNode`s and builds only the rows on screen. `TreeState` holds what is open, selected and checked, and where it has scrolled; the tree changes it as a person uses it, so the app reads it to follow along. `expandTo` and `reveal` bring a row into view. Arrows, Home, End, Page Up and Down move, and typing a name's first letters jumps to it; Shift and Ctrl (Cmd on macOS) extend the selection. `checkboxes = true` gives every row a box that checks everything under it, with mixed parents. `onActivate` gets Enter and double-clicks, and `trailing` holds counts and badges. `onContextMenu = { item, at -> ... }` asks for a row's menu on a right-click, a long press with a pen or finger, or Shift F10 and the Menu key on the focused row; a row outside the selection becomes the selection first, so the menu acts on `state.selection`. Show it with stretch-frame's `ContextMenuPopup(at, onDismiss) { close -> ... }` in a `Box` around the tree. Any menu can nest items under `SubMenuItem(text, icon) { ... }`, which opens its panel beside it on hover or click; its items call the menu's own `close`. `rowModifier` adds the app's own modifier to every row, such as `paneDragSource` to drag rows into a `PaneGrid`; with `onMove` too, rows still reorder, and a row let go off the tree's sides moves nothing. Text for screen readers is in `TreeStrings`.

## Pictures

`stretch-ui`'s `decodeImage(bytes)` turns a file's bytes into an `ImageBitmap`: PNG, JPEG, GIF (its first frame), WebP, BMP, ICO, and SVG drawn at the size it gives (or its view box), or null for anything else. `ImageView(image, contentDescription = ...)` shows one centred on a checkerboard that shows through transparency; a picture larger than the view shrinks to fit, and a click shows it at its own size, scrolling both ways, until another click fits it again.

## Paths

`PathLabel(path, style, color)` shows a file path on one line and keeps its file name: when the path is too wide, folders drop out of its middle (`src/main/…/ui/App.kt`), and only a name too wide on its own loses its middle too. Screen readers hear the whole path. `middleEllipsis(text, suffix) { fits(it) }` shortens any text the same way for a view that measures its own, and `splitPath` splits a path into its folders and its name.

## Documents

`stretch-document` keeps one open document: `DocumentSession(format, initial, documentStorage)` wraps its undo history and knows when it has unsaved changes (`rememberEdited`), even after undoing back to the save. `session.whenSaved { close() }` asks with `UnsavedChangesDialog` first when there are changes; `save`, `saveAs` and `open` use `rememberFileChooser()`, the platform's own dialogs: on Windows the shell's, the ones Explorer uses, with the format's files listed under its description, and AWT's elsewhere. `pickFiles` and `SystemFileDialogs` show the same dialogs for any files, a `FileKind` naming each kind of file listed. `Autosave(session, Recovery.forApp())` keeps a recovery copy while there are changes, and `Recovery.pending()` with `RecoveryDialog` offers them after a crash; storage, choosers and recovery are all `suspend`, since browsers answer later. `LeaveGuard(edited)` makes the browser ask before a tab with changes closes, and does nothing on the desktop. In a browser, documents live in files the person picks through the File System Access API, which also brings recent files back on a later visit once they allow it again; where a browser lacks that API, opening uses a file input and saving downloads the file. Recovery copies stay in IndexedDB, in that browser only. `RecentFiles` and `RecentFilesMenuItems` list recent files; keeping the list between runs is the app's job, like all its settings.

## Diffs

`stretch-diff`'s `DiffViewer(files)` shows `List<FileDiff>`: make them with `diffTexts(old, new, path)` from two whole texts, where a null path means that side has no file, or `parseUnifiedDiff(patch)` from `git diff` or `diff -u` output. Only rows on screen are built, so large diffs stay smooth. `rememberDiffViewerState(split, wrap)` holds the layout and scrolling; with `wrap`, long lines wrap with their numbers, gutter marks and selection on the first row, and side by side each row is as tall as its taller half so both halves stay level, with `nextChange()` and `previousChange()`; `showBar = false` hides the built-in bar for an app with its own controls. `DiffSlots` adds `onLineClick`, `lineAnnotation` under a line for threads of notes (side by side, called for each side's line in turn, old first; unified, once per line with its own side), `fileActions` and `hunkActions` for buttons like Stage, `gutterMark` before each side's numbers and `lineTone` to wash a line with a `LineTone`. With `onLineRangeSelect`, pressing and dragging over line numbers, or Shift-clicking them, selects lines on one side of one file: it gets a `DiffLineRange` with the file, the `DiffSide` and the first and last line, and `state.lineSelection` holds it until cleared. A side's gutter mark, number and sign answer as one target under a pointing hand, and in unified view the gutter and old number go with the old side, the new number and sign with the new, or all of it with a line's one number; a press there never starts a text selection or scrolls the code. To keep another view beside it in step, `state.firstVisibleLine(side)` gives the file and line at the top and `scrollToLine(file, side, line)` goes there; `list`, `leftScroll` and `rightScroll` are the scroll states themselves. Text is in `DiffStrings`. A file's language comes from its path, and the viewer tokenizes each hunk from its lines; an app that parses files itself passes `tokens = mapOf(file to FileTokens(old, new))`, whole-file tokens for each side as one list per line indexed by that side's line number, and files or sides it leaves out keep the built-in coloring. Tokens may arrive after the files, as from a background parse, and the view keeps its place. An app that finds text itself passes `matches`, a list of `DiffMatch(fileIndex, side, line, start, end)`, and `currentMatch`; they draw in place in the find bar's colors, the current one set apart, and `state.scrollToMatch(match)` opens the file and fold that hide it and scrolls it into view. `findInDiff(files, query, matchCase)` finds plain text that way, a removed line's matches on the old side and every other line's on the new. A ruler beside the scrollbar, on unless `ruler = false`, marks removed lines down its left half and added ones down its right, find matches and the app's `marks` (`DiffMark(fileIndex, side, line, color)`) down its middle, with a band for the part on screen; pressing or dragging on it scrolls there, and wrapped rows take their real share of it. A diff shorter than the view marks each line beside it, down only as far as the content reaches, and its scrollbar shows no thumb. `changeWash = ChangeWash.Gutter` washes added and removed lines behind their numbers and sign only, leaving the code on the plain surface.

`decorations` and clicking through to symbols work as in the code viewer (see [Code](#code)), on one side of one file at a time. `decorations` takes `DiffDecoration(fileIndex, side, range, style, tooltip)`, where `range.line` counts on that side; in one column, a line both sides share shows both sides' decorations. `DiffSlots(symbolAt = ..., onSymbolClick = ...)` asks with a `DiffPosition(fileIndex, side, line, column)`, wants a range on that same line back, and reports a `DiffSymbolClick(position, range, bounds)`. Side by side each half is its own side; in one column a removed line is old and every other line new. `state.caret` is a `DiffPosition`, and `state.clickSymbolAtCaret()` opens the file and fold that hide the name before clicking through. `DiffSlots(symbolCard = { position, range, card -> ... })` opens a symbol card as the code viewer does, with a `DiffPosition`. `blocks = listOf(DiffBlock(fileIndex, newLines))` with `DiffSlots(lineBlock = { block, side -> ... })` draws a run of unchanged lines as a block, once in one column and on each side when split; a run draws as code unless every line of it shows unchanged, in order.

## Code

`stretch-code`'s `CodeViewer(CodeText.of(text), language = CodeLanguages.forPath(path))` shows a whole text read-only, with line numbers and code colored, and builds only the lines on screen. Text selects across lines. `tones` washes whole lines with a `LineTone`, such as `Added` for changed lines, and lines toned `Added` or `Removed` get a bar of the strong diff color down their start edge unless `changeBars = false`, and `CodeViewerSlots` adds `gutterMark` before the numbers, `lineAnnotation` under a line and `onLineNumberClick`, which the gutter mark and number answer together under a pointing hand. Ctrl F (Cmd F on macOS) opens a find bar. `rememberCodeViewerState(wrap)` holds wrapping, finding and scrolling, and a wrapped line keeps its number and gutter mark on its first row; without wrapping, a line is laid out no wider than `MAX_CODE_WIDTH_PX` and cut there, in the diff viewer too: `scrollToLine(n)` goes to a line, and since each line is one item of its `list`, `alignLine` lets one viewer follow another's `firstVisibleItemIndex`. Text is in `CodeViewerStrings`. `tokens` colors the code from outside in place of `language`, one list of `CodeToken(start, end, kind)` per line with offsets within the line; `tokensByLine(text, spans)` splits a parser's spans over the whole text onto lines, and tokens that arrive after the text leave the view where it was. `matches` (a list of `CodeRange`) and `currentMatch` draw an app's own find matches, such as a regular expression's, in place of the find bar's, and `state.scrollToMatch(range)` scrolls one into view. A ruler beside the scrollbar, on unless `ruler = false`, marks toned lines, find matches and the app's `marks` (`CodeMark(line, color)`) along the whole text, and pressing or dragging on it scrolls there; it is `stretch-ui`'s `OverviewRuler(marks, length, onJump, shown = ...)`, which takes `RulerMark`s in any units, and `RulerRows` with `wrappedRows` places a lazy list's items on it by the rows of text they take. While the whole text shows with room to spare, its `fit = { rows.fit(list) }` puts each mark beside its line instead of spreading the text over the ruler's height, and `Scrollbar` shows no thumb while there is nothing to scroll. `CodeLineRow`, `CodeLineBody`, `codeLineText`, `rememberCodeMetrics` and `rememberCodeLook` draw lines the same way for other code views. `changeWash = ChangeWash.Gutter` moves the wash of `Added` and `Removed` lines onto the gutter and line number, leaving the code plain; other tones still wash the whole line.

`decorations`, a list of `CodeDecoration(range, style, tooltip)`, sets runs of code apart in one of a few `CodeDecorationStyle`s, all in the theme's colors: `Reference` and `Definition` wash behind the text, `Accent` draws a dotted underline, and `Warning` and `Error` wavy ones. Where decorations overlap, each character takes the strongest wash (`Definition` over `Reference`) and the strongest underline (`Error` over `Warning` over `Accent`), the two layers draw together, and find matches draw over washes. Warnings and errors also mark the ruler. While the pointer rests on a decoration with a tooltip, it shows over its range, together with the tooltips of any others there, the most severe first. Decorations are plain data, so they can come from anywhere, such as a plugin in another process.

With `CodeViewerSlots(symbolAt = ..., onSymbolClick = ...)`, names in the code click through. Holding Ctrl (Cmd on macOS) over the code asks `symbolAt(CodePosition(line, column))` what is under the pointer; it suspends, so the app can look it up off the UI thread, and the range it returns on that line draws underlined in the link color under a pointing hand. An answer slow to come leaves the last one underlined until it does, moving within an underlined name asks nothing, and an answer for a place the pointer has left is dropped. A Ctrl or Cmd click calls `onSymbolClick(CodeSymbolClick(position, range, bounds))`, where `bounds` is the range in pixels from the viewer's top left: a `Popover` or `Menu` from `stretch-frame` with `anchor = bounds`, composed in a `Box` the viewer fills, opens under the name. A Ctrl or Cmd press in the code never starts a selection; a plain press, click and drag select as always. A plain press also moves `state.caret`, a `CodePosition` the app can set too, such as on a definition it went to, and `state.clickSymbolAtCaret()` clicks through from it as a Ctrl click there would, scrolling the name into view first, for a key the app binds such as F12. With `symbolCard = { position, range, card -> ... }` as well, resting the pointer on a name for `SYMBOL_CARD_DELAY_MS` asks `symbolAt` there and opens the app's card under the name (over it when there is no room below), such as its signature and documentation; the content draws the whole card, and emitting nothing shows nothing. The card stays while the pointer is on the name or the card and closes `SYMBOL_CARD_GRACE_MS` after it leaves both, when the view scrolls, on a press in the code or on Escape; it never opens while Ctrl or Cmd is held or a button is down, and decoration tooltips wait while it is open. Setting `card.pinned` keeps it where it is until `card.close()` or Escape. `blocks = listOf(20..26)` with `CodeViewerSlots(lineBlock = { lines -> ... })` draws those lines as the app's content in place of their code, such as a doc comment rendered: the first line's gutter mark and number stay, a bracket runs down the numbers to the block's foot, the other lines take no room and their line annotations still show under it. Runs that overlap or fall outside the text are left out. `CodeSymbolPointer`, `rememberCodeSymbolInput`, `CodeDecorationTooltip`, `CodeSymbolCardPopup`, `decorationPaint` and `CodeLineBody`'s `underlines` give other code views the same.

## Console

`stretch-console`'s `Console(rememberConsoleState())` shows what a process prints, building only the lines on screen. Feed it with `state.append(text, ConsoleStream.Out)` or `feed(flow)` on the UI thread: it follows ANSI colors and styles (the first 16 colors follow the theme), rewrites a line on a carriage return as progress bars expect, and keeps the last `maxLines`. It follows new output until someone scrolls up, then offers a button back to the end; `clear()` empties it. Ctrl F (Cmd F on macOS) finds. `links` finds what to make clickable, by default `PathLineLinks` for `path:line[:column]`, and `onLinkClick` gets the `ConsoleLink`. On the desktop, `state.runProcess(ConsoleCommand(listOf("git", "status"), folder, env))` runs a program with no shell between, streams both outputs in and returns its exit code; its `onStart` gets the `ProcessHandle` once the program runs. Cancel the coroutine to end it and everything it started. Text is in `ConsoleStrings`.

## Markdown

`stretch-markdown`'s `MarkdownEditor(state)` edits `rememberMarkdownEditorState(text)`; read `state.text` for the markdown, and `state.setText` to replace it. `state.history` is a Stretch `History`, so a `DocumentSession` given that history tracks unsaved changes, and typing in one go is one undo step.

`MarkdownMode.LivePreview` shows the markers of the block with the caret, and `MarkdownMode.Wysiwyg` never shows them; in both, typing `## ` or `**word**` becomes formatting. Set the mode with `state.mode`. `modes` lists what the app offers: `modes = MarkdownMode.entries` puts a switch in the toolbar, one mode shows none. `readOnly = true` makes it a viewer that fills the height it is given.

`MarkdownView(text, modifier, images, onLinkClick, strings, diagrams)` shows markdown read-only and only as tall as its content, so it sits in a card or a scrolling column of comments; it has no toolbar and no scrolling of its own, and its text selects. Its blocks draw as the editor draws them, and it also draws the HTML GitHub comments use: `<details>` with its `<summary>` (closed until clicked), paragraphs, line breaks, headings, lists, quotes, `<pre>`, inline styles including `<sub>` and `<sup>`, links, `<img>`, rules and tables. HTML comments and link reference definitions show nothing, tags it does not know show their text, and character references are decoded. A tag opened in one HTML block holds the markdown blocks up to its closing tag, as GitHub reads Dependabot's descriptions. Pictures, from `![alt](url)` or `<img src alt width>`, load through `images` and show under their text, opening the link around them when clicked; a bare address is a link.

A block is one heading, paragraph, list item, quote, GitHub alert (`> [!NOTE]`), fenced code, table, image or divider. Anything else, like HTML and front matter, stays as source in the editor. Blocks no one edits stay byte for byte, line endings included; an edited table is padded so its columns line up in the file. On screen a table sizes its columns to their text, as a web page does: long cells wrap and their rows grow, and only a table whose words cannot fit side by side scrolls sideways. Cmd or Ctrl with B, I, E and K format the selection, Ctrl Shift X strikes through, Tab nests a list item, `/` in an empty block lists the block types, and Ctrl A twice or Shift with an arrow at a block's edge selects whole blocks to copy, cut or delete. Text selections stay within one block.

Pass `images` to load pictures, since Stretch has no network of its own, and `diagrams` to draw diagrams; without them pictures show as a marked placeholder and diagrams as code. `DiagramRenderer` can draw any language. `onLinkClick` gets a link clicked with Cmd or Ctrl held, or any click in a viewer. Text is in `MarkdownStrings`.

## Web pages and Mermaid

`stretch-web`'s `HtmlView(HtmlContent.Inline(html))` or `HtmlContent.Url(url)` shows a page. Pages cannot open windows, download files, show dialogs or ask for permissions. Links go to `navigation`, which keeps the view where it is unless it returns true, so an app can open them in the person's browser. `HtmlPolicy(scripts, network)` limits an inline document, and nothing in the document can lift that. An inline document with no background shows the theme behind it, and starts from the theme's text color and light or dark. `ScriptPage` runs a JavaScript library in a hidden page. The page sees the theme too: every color token, the radii and the stroke are CSS custom properties on its root, such as `var(--stretch-surface-canvas)` and `var(--stretch-radius-ctl)`.

To talk with a page, pass `HtmlView` a `rememberHtmlBridge { message -> ... }`. The page sends strings with `stretch.post(text)` and hears the app through `stretch.listen(fn)`; `window.stretch` is there before an inline document's own scripts run, and other pages can wait for the `stretch-ready` event. The app sends with `bridge.post(text)`, which waits until the page is ready, and hears the page on the UI thread. Send JSON for anything richer than a string. In a browser a `Url` page gets neither the bridge nor the theme, since its document is not Stretch's to change: it posts `stretch-message:` and the text to its parent itself, and hears messages that start the same way.

`stretch-mermaid`'s `MermaidDiagrams()` draws `mermaid` blocks: pass one, kept with `remember`, as the editor's `diagrams`. The first diagram takes a few seconds to start the engine and shows its code until then.

`EngineWork` is a `Settled` that is settled while the engine has nothing under way: on the desktop no `HtmlView` waits for its first picture of the page it shows, no `ScriptPage` runs a script and no diagram is drawing. A library that drives a `ScriptPage` through steps of its own wraps them in `EngineWork.during { }`. Tests wait for it rather than for time to pass (see [Tests](#tests)).

On the desktop the engine is the JCEF in the JetBrains Runtime. Run and package the app with one (see `gallery/build.gradle.kts` for the toolchain line), and apply the `dev.chieppa.stretch.app` plugin: it adds Chromium to the package when the app depends on `stretch-web` or `stretch-mermaid`, and leaves it out otherwise. On Windows that takes a package from about 145 MB to about 515 MB. Set `stretchApp { webEngine = true }` if they arrive through another library of the app's. `WebEngine.available` is false on a runtime without JCEF, where `HtmlView` shows `unavailable` and diagrams show as code. Input methods, such as those for CJK languages, do not reach a page.

An app that runs without JCEF, from a jar on any Java or packaged with `stretchApp { fetchWebEngine = true }`, can fetch the engine while it runs. `WebEngine.requirement` is a `Requirement` from `stretch-core`: `install()` downloads JetBrains' runtime with JCEF for this computer (about 250 MB), checks it against the SHA-512 Stretch pins, and unpacks it into the user's Stretch folder, which every Stretch app shares, so it is fetched once per machine. It works in the background, apart from any screen, and `state` reports `Missing`, `Installing` with bytes, `NeedsRestart`, `Failed` or `Ready`; `cancel()` stops it and removes the partial files. `restart()` starts the app again on that runtime, so save first. Call `WebEngine.startOnInstalledRuntime(args)` first in `main`: on a Java without JCEF, once the runtime is there, it runs the app on it and exits with it, so this process waits beside it. `RequirementRow` in `stretch-frame` shows any requirement with its get, progress, cancel and restart, in the app's words through `RequirementStrings`. `Requirements.all` lists what the app's modules need; modules add theirs through `META-INF/services/dev.chieppa.stretch.core.Requirement`.

In the browser `HtmlView` is a sandboxed iframe. It sits above the Compose canvas, so popups cannot cover it, a `Url` page's links stay in the frame, and with `scripts = false` links in an inline document do too. A site can refuse to be framed.

## App identity

The `dev.chieppa.stretch.app` Gradle plugin (in `stretch-gradle-plugin/`) gives the app one name, id and icon everywhere: the packaged launcher and installers, the taskbar, dock and Start menu, and Task Manager, which shows the launcher's name instead of "OpenJDK Platform binary". It's published with the modules, so add the same GitHub Packages repository to the app's `pluginManagement`, then apply it in the app module, next to the Compose plugin:

```kotlin
plugins { id("dev.chieppa.stretch.app") version "<version>" }

stretchApp {
    name = "Squash"
    id = "dev.chieppa.squash"
    icon = layout.projectDirectory.file("app-icon.png") // square PNG (1024px best) or an SVG
}
```

An SVG icon is drawn at every size the icon files hold; a hand-tuned `<name>-<size>.svg` beside it, such as `app-icon-16.svg`, is drawn for that size instead, for the small sizes where the full drawing loses detail.

The plugin covers desktop packaging. In a multiplatform module, add its generated resources to the desktop source set, as `gallery/build.gradle.kts` does.

It fills in Compose's `nativeDistributions` (name, description, numeric version, which on macOS is 1.0.0 until the app reaches 1.0 since macOS takes no version starting with 0, icons, macOS bundle id, Windows upgrade id) unless the app set them, and puts the icon and identity on the classpath so `StretchWindow` badges its windows at every size. `./gradlew :app:runDistributable` runs through the real launcher; plain `run` is still `java.exe` to Task Manager, but the window, taskbar button and taskbar grouping carry the app's icon and id.

## Tests

`stretch-test` holds what an app's tests need to wait on events rather than time: `scenario` for commands, `TestSettled` and `awaitSettled` for derived data, and `setStretchContent` and `inEveryTheme` for Compose UI tests, whose `waitForIdle` and virtual `mainClock` cover composition and its effects. Work Compose cannot see, such as the browser engine drawing, goes through a `Settled`: on the desktop, `runComposeUiTestAwaiting(EngineWork) { ... }` runs a Compose UI test whose `waitForIdle`, and every wait built on it, also waits until each `Settled` it is given is. Storage given to a `DocumentSession` runs on the caller's thread unless it moves blocking work off it itself, as `documentStorage` does, so a session over storage in memory saves within `waitForIdle`. On the desktop, `pointerIconsAt(size, points) { ... }` lays content out with no window, moves the mouse to each point and returns the pointer icon shown there.

## Apps run from a jar

An app handed out as a jar needs no signing: the OS checks the Java runtime that runs it, and the window, taskbar, dock and menu bar already carry the app's name and icon. `AppLauncher` in `stretch-frame` gives it a way to start like any other app: `install()` makes a Start menu shortcut on Windows, an app in `~/Applications` on macOS or a desktop entry on Linux, with the app's name and icon, starting it as the running process was started and on the same Java. The app makes these files itself, so no OS treats them as downloaded. Call `AppLaunch.remember(args)` first in `main` (`WebEngine.startOnInstalledRuntime` does) so the launcher keeps the app's arguments, and install again after a move to another runtime. `installed()` and `remove()` go with it; it is not `available` in a packaged app, which has a launcher already. Task Manager still names the process after `javaw.exe`.
